### Hallazgos

#### 1. Token marcado activo antes de que el login pueda fallar (correctness)
**Archivo:** `BACKEND/app/routers/auth.py` — línea donde se llama `marcar_activa(token_hash)` antes del bloque `try`.

`marcar_activa` se invoca antes de intentar el `db.commit()`. Si alguna validación posterior dentro del `try` lanza una excepción no relacionada con la sesión (por ejemplo, un fallo al registrar la auditoría que burbujee antes de `db.rollback()`), el token habrá sido marcado activo en caché aunque el flujo de login no haya concluido normalmente. El TTL de 30 s mitiga el riesgo, pero supone una ventana de validez de token sin sesión correspondiente en BD.

**Mejora sugerida:** Envolver `marcar_activa` en un punto lo más cercano posible a la devolución de la respuesta (`return`), o añadir en el bloque `except` una llamada a `invalidar(token_hash)` para retirar la entrada de la caché si el `commit` falla definitivamente.

#### 2. Dos bucles separados para emitir y cerrar sockets en `_emitir_y_cerrar_usuario` (ineficiencia menor)
**Archivo:** `BACKEND/app/core/session_events.py` — método `_emitir_y_cerrar_usuario`, líneas donde se itera `sockets` dos veces.

```python
for ws in sockets:
    await self._enviar(ws, payload)   # primer bucle
for ws in sockets:
    try:
        await ws.close(code=4002)     # segundo bucle
    except Exception:
        pass
```

`_enviar` ya absorbe sus propias excepciones internamente, así que el comportamiento observable es el mismo que con un bucle único. La iteración doble no causa bugs, pero es redundante y aumenta el tiempo de espera total cuando hay muchas conexiones abiertas (se termina de enviar a todos _antes_ de empezar a cerrar, en vez de proceder en paralelo).

**Mejora sugerida:** Fusionar en un único bucle:
```python
for ws in sockets:
    await self._enviar(ws, payload)
    try:
        await ws.close(code=4002)
    except Exception:
        pass
```

#### 3. Header CORS ausente en respuesta de error 500 (UX/compatibilidad)
**Archivo:** `BACKEND/app/main.py` — `unhandled_exception_handler`.

La respuesta 500 anterior incluía `headers={"Access-Control-Allow-Origin": "*"}`. Al eliminarla, los errores 500 en solicitudes cross-origin serán bloqueados por el navegador antes de que el frontend pueda leer el cuerpo (lo interpreta como fallo de red). El mensaje genérico que se devuelve actualmente no supone un riesgo de fuga, pero puede dificultar el diagnóstico en el cliente.

**Mejora sugerida:** Si el frontend necesita leer el body del 500, añadir la cabecera `Access-Control-Allow-Origin` en la respuesta de error de forma restringida (o dejar que el `CORSMiddleware` la inyecte). Alternativamente, documentar que los 500 se tratarán como errores de red en el cliente.

### Hallazgos

#### 1. `contentType.split('/')` sin validación puede lanzar `RangeError` (bug de correctness)
**Archivo:** `e_zyro_app/lib/core/api_client.dart` — método `postMultipartBytes`, líneas:
```dart
final parts = contentType.split('/');
...
contentType: MediaType(parts[0], parts[1]),
```

Si `contentType` no contiene `/` (por ejemplo, una cadena vacía, `"pdf"` o un valor mal formado), `parts[1]` lanzará un `RangeError` en tiempo de ejecución. Actualmente el valor por defecto es `'application/pdf'`, que es correcto, pero cualquier llamada futura con un tipo incorrecto romperá la aplicación sin mensaje claro.

**Mejora sugerida:**
```dart
final slashIdx = contentType.indexOf('/');
if (slashIdx == -1) throw ArgumentError('contentType must be "type/subtype", got: $contentType');
final parts = [contentType.substring(0, slashIdx), contentType.substring(slashIdx + 1)];
```

#### 2. Envío masivo de boletas completamente secuencial (ineficiencia)
**Archivo:** `e_zyro_app/lib/screens/finanzas/pantalla_planilla.dart` — método `_vpProcesarEnvioMasivo`.

```dart
for (var i = 0; i < emps.length; i++) {
  final bytes = await PdfService.boletaPago(...);   // genera PDF
  final r = await svc.enviarBoletaALegajo(...);     // sube al servidor
  ...
}
```

Cada empleado espera a que el anterior termine de generar el PDF _y_ hacer el upload antes de empezar. Para 20 empleados esto supone ~40 operaciones async en serie. El tiempo total crece linealmente con el número de empleados.

**Mejora sugerida:** Procesar en lotes concurrentes con `Future.wait`:
```dart
const kBatchSize = 4;
for (var i = 0; i < emps.length; i += kBatchSize) {
  final lote = emps.sublist(i, min(i + kBatchSize, emps.length));
  await Future.wait(lote.map((e) async {
    try {
      final bytes = await PdfService.boletaPago(empleado: e, ...);
      final r = await svc.enviarBoletaALegajo(e.id, bytes, ...);
      if (r.ok) enviados++ else errores++;
    } catch (_) { errores++; }
  }));
  setState(() => _vpMasivoProgreso = 'Procesando ${min(i + kBatchSize, emps.length)} / ${emps.length}…');
}
```
Un lote de 4 concurrentes reduce el tiempo de espera a ~25 % del actual sin saturar la red del dispositivo.

#### 3. Getters `_documentosFiltrados` y `_filtrados` recalculados en cada `build()` (ineficiencia menor)
**Archivos:**
- `e_zyro_app/lib/screens/pantalla_legajo_detalle.dart` — getter `_documentosFiltrados`
- `e_zyro_app/lib/screens/pantalla_legajo_lista.dart` — getter `_filtrados`

Ambos getters iteran la lista de documentos/empleados completa en cada llamada a `build()`. Para listas pequeñas (< 50 elementos) el impacto es mínimo, pero si el número de empleados crece, el scroll o cualquier setState disparado por animaciones recalculará el filtro innecesariamente.

**Mejora sugerida:** Cachear el resultado en una variable de estado y actualizarla solo cuando cambia `_busqueda` o `_categoria`:
```dart
// En initState / _cargar / onChanged:
_empleadosFiltrados = _calcularFiltro(_busqueda);
setState(() {});
```

#### 4. `setState` en el listener de `TabController` provoca rebuild completo (ineficiencia menor)
**Archivo:** `e_zyro_app/lib/screens/finanzas/pantalla_planilla.dart` — `initState`.

```dart
_tabs.addListener(() {
  if (!_tabs.indexIsChanging) setState(() {});
});
```

Este `setState` vacío reconstruye el árbol entero de `PantallaPlanilla` (incluidos los cuatro tabs de la planilla, que ahora tienen lógica considerablemente más pesada con la nueva vista previa). El único dato que cambia es `_tabs.index`, usado únicamente para decidir qué `FloatingActionButton` mostrar.

**Mejora sugerida:** Envolver solo el `FloatingActionButton` en un `AnimatedBuilder` ligado al `TabController`:
```dart
floatingActionButton: AnimatedBuilder(
  animation: _tabs,
  builder: (_, __) => _buildFab(),
),
```
Esto evita el rebuild completo de las tabs en cada cambio de pestaña.
