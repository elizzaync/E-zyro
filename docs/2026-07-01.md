### Hallazgos

#### 1. BUG — Estado incorrecto para CxC parciales en el dashboard financiero

**Archivo:** `BACKEND/app/services/reportes_financieros_service.py` — función `_documentos_abiertos`, línea 257 del archivo resultante.

**Código problemático:**
```python
.filter(Doc.empresa_id == empresa_id,
        Doc.estado.in_(("pendiente", "pagada_parcial")))
```

Esta misma condición se aplica a CxC **y** a CxP. Sin embargo:
- En `cuentas_por_pagar_service._estado_por_saldo`, el estado parcial es `"pagada_parcial"` ✓ correcto para CxP.
- En `cuentas_por_cobrar_service._estado_por_saldo`, el estado parcial es **`"cobrada_parcial"`**, no `"pagada_parcial"`.

**Impacto:** Todas las facturas de clientes con cobro parcial (estado `cobrada_parcial`) son **ignoradas** por la query de CxC. El KPI "Te deben" del dashboard mostrará un valor menor al real, y la proyección de caja a 30/60/90 días no incluirá los cobros pendientes de esas facturas.

**Corrección:**
```python
# Para CxC usar "cobrada_parcial"; para CxP usar "pagada_parcial"
if lado == "cxp":
    estados_pendientes = ("pendiente", "pagada_parcial")
else:
    estados_pendientes = ("pendiente", "cobrada_parcial")
...
.filter(Doc.empresa_id == empresa_id,
        Doc.estado.in_(estados_pendientes))
```

#### 3. Optimización — Tendencia puede recortarse en SQL (`indicadores.py`)

**Archivo:** `BACKEND/app/routers/indicadores.py` — función `_tendencia_por_empleado`.

La función carga **todos** los periodos de evaluación de todos los empleados y luego recorta en Python a los últimos `max_periodos=6`. Con muchos empleados y muchos periodos históricos, la query devuelve filas extra que se descartan.

Sugerencia: la query actual es suficientemente eficiente para volúmenes normales (la query ya está agrupada y no es N+1). No es urgente, pero se podría usar `ROW_NUMBER() OVER (PARTITION BY empleado_id ORDER BY fecha DESC)` para recortar en SQL si se detecta lentitud.

#### 2. `moduloFinanzasPorId` se llama dos veces por elemento en `_accionesRapidas`

**Archivo:** `e_zyro_app/lib/screens/finanzas/pantalla_finanzas.dart` — método `_accionesRapidas`.

```dart
final visibles = [
  for (final a in acciones)
    if (moduloFinanzasPorId(s, a.$3) != null) a,  // 1ª llamada (filtro)
];
// …
onTap: () {
  final m = moduloFinanzasPorId(s, visibles[i].$3);  // 2ª llamada (en tap)
```

`moduloFinanzasPorId` se invoca una vez para filtrar y otra vez en cada `onTap`. Siendo solo 3 elementos es inofensivo en práctica, pero el módulo ya se encontró en el filtro. Se puede guardar en la tupla para evitar la búsqueda duplicada:

```dart
final visibles = [
  for (final a in acciones)
    if (moduloFinanzasPorId(s, a.$3) case final m?) (a, m),
];
// …
onTap: () => Navigator.push(context, MaterialPageRoute(builder: visibles[i].$2.builder)),
```

#### 4. `setState` innecesario en `_cargar` cuando el widget no está montado

**Archivo:** `e_zyro_app/lib/screens/finanzas/pantalla_finanzas.dart` — método `_cargar`.

```dart
Future<void> _cargar() async {
  if (_svc == null) return;
  setState(() { _cargando = true; _error = null; });  // ← puede llamarse antes de que el widget esté en el árbol
  final r = await _svc!.resumenFinanciero();
  if (!mounted) return;                               // guarda correcta después del await
  setState(() { … });
}
```

La guarda `if (!mounted) return` solo aparece después del `await`. El primer `setState` se ejecuta siempre que `_svc != null`, incluso si el widget fue desmontado antes de que `_cargar` corriera (por ejemplo, si se llama desde `initState` y el widget se destruye inmediatamente). Se debería añadir `if (!mounted) return;` justo antes del primer `setState`:

```dart
Future<void> _cargar() async {
  if (_svc == null) return;
  if (!mounted) return;
  setState(() { _cargando = true; _error = null; });
  final r = await _svc!.resumenFinanciero();
  if (!mounted) return;
  setState(() { … });
}
```
