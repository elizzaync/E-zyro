### Hallazgos

#### H1 — Bucle lineal triple sobre `regs` por empleado
**Archivo:** `BACKEND/app/services/planilla_asistencia_service.py`, líneas ~163–175 (patrón presente desde `f9c2908c`, agravado en `ee9d1a25`)

Dentro del loop principal por empleado, la lista `regs` (marcaciones del período para ese empleado) se recorre linealmente una vez por cada domingo, una vez por cada feriado trabajable y una vez por cada día laborable mediante comprensiones de lista del tipo `[r for r in regs if r.fecha_hora.date() == dia]`. En un mes típico con 4 domingos + 10 feriados + 22 días laborables = 36 pasadas lineales sobre `regs`. Para una empresa con empleados con muchas marcaciones, el costo es O(36 × |regs|) por empleado.

**Mejora sugerida:** Agrupar `regs` por fecha en un diccionario una sola vez antes de los tres loops:
```python
regs_by_date: dict = {}
for r in regs:
    regs_by_date.setdefault(r.fecha_hora.date(), []).append(r)
```
Luego sustituir `[r for r in regs if r.fecha_hora.date() == dia]` por `regs_by_date.get(dia, [])` en los tres loops. Esto reduce el costo de búsqueda de O(|regs|) a O(1) por día especial.

#### H2 — `datetime.utcnow()` deprecado en Python 3.12
**Archivo:** `BACKEND/app/services/audit_service.py`, línea 121 (commit `e20c32ff`)

El campo `fecha` de cada evento de auditoría se genera con `datetime.utcnow()`, que fue marcado como deprecado en Python 3.12 (PEP 615) y emite `DeprecationWarning`. El resultado es un datetime "naive" (sin tzinfo), lo que puede causar comparaciones incorrectas si en algún punto se mezcla con datetimes timezone-aware.

**Mejora sugerida:**
```python
from datetime import timezone
# ...
fecha=datetime.now(timezone.utc),
```
