### Hallazgos

#### 1. Bug corregido (mismo día): `replace()` con minutos + tolerancia ≥ 60 → `ValueError`

**Archivo:** `BACKEND/app/routers/rrhh_asistencia.py`, función `_estado_dia_turno` (~línea 85, introducido en `542fe046`, corregido en `0af2fa8a`)

El límite de tardanza se calculaba como:
```python
limite = entrada.fecha_hora.replace(
    hour=hora_entrada_turno.hour,
    minute=hora_entrada_turno.minute + tolerancia_min,  # overflow si minutos ≥ 60
    ...
)
```
Para un turno que comienza a las 07:55 con tolerancia de 10 minutos, `minute=65` lanza `ValueError`. Cualquier petición de reporte con ese turno causaría un error 500.

**Corrección aplicada:** `datetime.combine(entrada.fecha_hora.date(), hora_entrada_turno) + timedelta(minutes=tolerancia_min)`.

#### 4. Consultas DB duplicadas en `_xlsx_mensual_gerencial`

**Archivo:** `BACKEND/app/routers/rrhh_asistencia.py`, líneas ~1502 y ~1515

La función comienza llamando a `_build_cronograma(...)`, que ya ejecuta consultas para `Empleado+Usuario` y todos los `RegistroAsistencia` del período. Inmediatamente después, `_xlsx_mensual_gerencial` emite dos consultas adicionales independientes con el mismo alcance:

```python
# línea ~1502: re-consulta Empleado+Usuario para construir nombre→id
emp_id_map = { f"{u.nombre} {u.apellido}".strip(): e.id
               for e, u in db.query(Empleado, Usuario).filter(...).all() }

# línea ~1515: re-consulta todos los RegistroAsistencia del mes
todos_regs = db.query(RegistroAsistencia).filter(...).all()
```

Para empresas grandes (ej. 100 empleados, mes completo), esto triplica innecesariamente las lecturas a la BD por cada solicitud de informe xlsx.

**Sugerencia:** Que `_build_cronograma` incluya `empleado_id` en cada elemento de `emps_data`, y que devuelva también el índice `regs_x_dia` ya construido (o que `_xlsx_mensual_gerencial` reciba los datos como parámetro en lugar de reconstruirlos).

#### 6. Inconsistencia en cálculo de tardanza en `dashboard.py`

**Archivo:** `BACKEND/app/routers/dashboard.py`, función `obtener_asistencia_perfil` (~línea 1020)

La tardanza se calcula con aritmética de minutos directa:
```python
actual_min  = entrada_dt.hour * 60 + entrada_dt.minute
limite_min  = hora_turno.hour * 60 + hora_turno.minute + tol
tardanza    = actual_min > limite_min
```

Si un turno comienza a las 23:55 con tolerancia de 10 minutos, `limite_min = 1445 > 1439 (máximo de actual_min)` → nunca se puede marcar tardanza. Caso borde poco probable pero inconsistente con el enfoque correcto (`datetime.combine + timedelta`) usado en `_estado_dia_turno` de `rrhh_asistencia.py`.

**Sugerencia:** Usar el mismo patrón: `limite = datetime.combine(fecha, hora_turno) + timedelta(minutes=tol); tardanza = entrada_dt > limite`.

#### 8. Inconsistencia entre `horas_reales` y `horas_justificadas`

**Archivo:** `BACKEND/app/routers/rrhh_asistencia.py`, `_build_resumen_full` (~líneas 748–765)

Los días justificados suman `META_HORAS_DIA` (constante global, presumiblemente 8h) a `horas_reales`:
```python
if dia in dias_justificados:
    horas_reales += META_HORAS_DIA  # siempre 8h
    continue
```

Sin embargo, `horas_justificadas` se calcula usando la duración real del turno del empleado:
```python
horas_justificadas = sum(_turno_emp_dia(emp.id, d)[2] for d in dias_justificados ...)
```

Si el turno de un empleado es de 6h/día, un día justificado le agrega 8h a `horas_reales` pero `horas_justificadas` reporta 6h. La inconsistencia produce porcentajes de cumplimiento sobreestimados para empleados con turnos cortos.

**Sugerencia:** Usar también `_turno_emp_dia(emp.id, dia)[2]` al acumular `horas_reales` en los días justificados.
