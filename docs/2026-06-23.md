### Hallazgos

#### 1. Bug — `cambiar_estado` acepta estados arbitrarios sin validación de permisos
**Archivo:** `BACKEND/app/routers/evaluaciones.py` (función `cambiar_estado`, commit `2e24903f`)

El bloque original `if/else` fue reemplazado por `if/elif` sin rama `else`:

```python
if body.estado == "enviada":
    exigir_permiso(...)
elif body.estado == "completada":
    exigir_permiso(...)
# ← sin else
ev.estado = body.estado   # se ejecuta para cualquier valor
db.commit()
```

Si `body.estado` es cualquier cadena distinta de "enviada" o "completada" (por ejemplo `"asignada"`, `"borrador"`, o cualquier valor arbitrario), no se verifica ningún permiso y el estado se persiste igualmente. Cualquier usuario autenticado puede llevar una evaluación a un estado no controlado.

**Sugerencia:** Agregar `else: raise HTTPException(status_code=422, detail="Estado no válido")` después del `elif`.

#### 2. Optimización — N+1 queries en `_eval_out` al listar evaluaciones
**Archivo:** `BACKEND/app/routers/evaluaciones.py` (función `_eval_out`, commit `2e24903f`)

Cuando una evaluación tiene `plantilla_id`, se hace una consulta individual a la base de datos para obtener el nombre de la plantilla:

```python
if ev.plantilla_id:
    pl = db.query(PlantillaEvaluacion).filter(PlantillaEvaluacion.id == ev.plantilla_id).first()
```

`_eval_out` es llamada en un loop desde el endpoint `listar`. Con 30 evaluaciones que tengan plantilla, esto genera 30 queries adicionales. El problema se replica también en `asignar_plantilla` donde `_eval_out(db, ev, con_detalles=True)` se llama dentro del `for emp_id in ...`.

**Sugerencia:** Antes del loop de serialización, precargar las plantillas necesarias en un solo query con `.filter(PlantillaEvaluacion.id.in_(ids_con_plantilla)).all()` y construir un dict `{p.id: p.nombre}` para lookup O(1).

#### 3. Optimización — N+1 queries al resolver empleados en `asignar_plantilla` y `crear_lote`
**Archivo:** `BACKEND/app/routers/evaluaciones.py` (funciones `asignar_plantilla` y `crear_lote`, commits `2e24903f` y `74d249e5`)

Dentro del bucle principal de ambas funciones:

```python
for emp_id in list(set(body.empleado_ids)):
    emp = db.query(Empleado).filter(
        Empleado.id == emp_id, Empleado.empresa_id == empresa_id).first()
```

Para 20 empleados esto emite 20 consultas individuales. El patrón correcto es cargar todos de una sola vez:

```python
emps = {str(e.id): e for e in db.query(Empleado).filter(
    Empleado.id.in_(ids_objetivo),
    Empleado.empresa_id == empresa_id,
).all()}
```

Y luego usar `emps.get(emp_id)` dentro del loop.

#### 4. Código — `from datetime import datetime` dentro de funciones
**Archivo:** `BACKEND/app/routers/evaluaciones.py` (funciones `editar_plantilla` y `eliminar_plantilla`, commit `2e24903f`)

```python
def editar_plantilla(...):
    ...
    from datetime import datetime      # ← import local
    p.updated_at = datetime.utcnow()
```

Este import local se repite en dos funciones distintas. `datetime` debería importarse al inicio del módulo junto al resto de imports. No genera un error en tiempo de ejecución, pero es inconsistente con el estilo del resto del proyecto y ejecuta la resolución del import en cada llamada.

**Sugerencia:** Agregar `from datetime import datetime` al bloque de imports del módulo (ya existe `from datetime import date`; ampliar a `from datetime import date, datetime`).

### Hallazgos

#### 1. Bug — Spinner de carga infinita si `getEvaluacionService()` falla en `_init`
**Archivo:** `e_zyro_app/lib/screens/pantalla_plantillas_evaluacion.dart` (método `_init`)

```dart
Future<void> _init() async {
  _svc = await getEvaluacionService();   // puede lanzar excepción
  await _cargar();
}

Future<void> _cargar() async {
  if (_svc == null) return;              // retorna sin cambiar _cargando
  setState(() { _cargando = true; ... });
  ...
}
```

Si `getEvaluacionService()` lanza una excepción (sin conexión, token inválido, etc.), `_svc` queda `null`. `_cargar` retorna inmediatamente sin ejecutar `setState`, por lo que `_cargando` permanece en `true` desde el estado inicial y el widget muestra `CircularProgressIndicator` indefinidamente sin mensaje de error ni posibilidad de reintentar.

**Sugerencia:**

```dart
Future<void> _init() async {
  try {
    _svc = await getEvaluacionService();
    await _cargar();
  } catch (_) {
    if (!mounted) return;
    setState(() { _cargando = false; _error = 'Error al inicializar el servicio'; });
  }
}
```

#### 3. Optimización — Descarga completa del historial para mostrar solo 4 jornadas
**Archivo:** `e_zyro_app/lib/screens/pantalla_mi_espacio.dart` (función `_cargar` y `_agruparJornadas`)

```dart
final histF = asis.getHistorial();       // trae TODOS los registros
...
_jornadas = _agruparJornadas(hist);      // agrupa y luego take(4)
```

`_agruparJornadas` itera el historial completo y al final llama `.take(4)`. Para un empleado con varios meses de registros, esto descarga centenares de objetos para mostrar solo 4 filas. El ancho de banda y la memoria usados escalan con la antigüedad del empleado.

**Sugerencia:** Añadir un parámetro `limit` o `desde` en el endpoint de historial del backend, o filtrar por fecha (últimos 7 días) antes de enviar la respuesta, y pasar ese parámetro desde el servicio Flutter.
