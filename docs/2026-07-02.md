#### 1. Consulta N+1 en `items_pendientes_retorno_servicio`

**Archivo:** `BACKEND/app/routers/logistica.py` — función `items_pendientes_retorno_servicio` (añadida en `4ce3cb11`)

**Problema:** Dentro del bucle `for d in detalles:`, por cada ítem que tiene `material_id` se emite una query individual al motor:

```python
if d.material_id:
    mat = db.query(Material).filter(Material.id == d.material_id).first()
```

Si un servicio tiene 20 ítems aprobados con material, se ejecutan 20 `SELECT` adicionales. El endpoint está pensado para la app móvil, que lo llama cada vez que el técnico entra a un servicio completado.

**Mejora sugerida:** Recolectar todos los `material_id` antes del bucle y cargarlos en una sola consulta `.in_()`:

```python
mat_ids = [d.material_id for d in detalles if d.material_id]
mats_by_id = {
    str(m.id): m
    for m in db.query(Material).filter(Material.id.in_(mat_ids)).all()
} if mat_ids else {}

for d in detalles:
    mat = mats_by_id.get(str(d.material_id)) if d.material_id else None
    ...
```

#### 3. Lógica de clasificación de tipo triplicada

**Archivos:** `BACKEND/app/routers/logistica.py` — funciones `items_pendientes_retorno_servicio`, `_req_out` y `crear_retorno_desde_servicio`

**Problema:** La misma cadena `if/elif` para clasificar un ítem como `"material"` / `"herramienta"` / `"equipo"` aparece copiada en tres lugares distintos. Incluso el comentario en `3e305a26` lo reconoce: *"Es la MISMA regla que crear_retorno_desde_servicio e items_pendientes_retorno_servicio"*. Esto es técnicamente un riesgo: un cambio futuro en la clasificación requiere actualizarse en tres sitios; si se olvida uno, el comportamiento diverge entre endpoints (el web que usa `_req_out` y la app que usa `items_pendientes_retorno_servicio`).

**Mejora sugerida:** Extraer en una función auxiliar privada del módulo:

```python
def _clasificar_tipo_item(
    tipo_item_compra: str | None,
    material: Material | None,
    equipo_id: str | None,
) -> str:
    explicit = (tipo_item_compra or "").lower()
    if explicit in ("material", "herramienta", "equipo"):
        return explicit
    if equipo_id:
        return "herramienta"
    if material and material.tipo == "herramienta":
        return "herramienta"
    return "material"
```

#### 1. TextField sin actualización visual cuando la cantidad se acota

**Archivo:** `e_zyro_app/lib/screens/detalle_servicio/retorno_sheet.dart` — clase `_ItemRetornoTileState`, método `build` → `TextField.onChanged`

**Problema:** Cuando el usuario escribe un valor fuera del rango `[0, cantidadEntregada]`, el callback acota el valor en el modelo (`it.cantidadRetornada = n`) pero no actualiza el `TextEditingController` ni llama a `setState`. El resultado visible: si `cantidadEntregada` es 5 y el usuario escribe "100", el campo sigue mostrando "100" mientras el modelo guarda 5. El usuario no recibe ninguna señal de que el valor fue rechazado.

```dart
onChanged: (v) {
  var n = int.tryParse(v) ?? 0;
  if (n < 0) n = 0;
  if (n > it.cantidadEntregada) n = it.cantidadEntregada;
  it.cantidadRetornada = n;   // el modelo se acota…
                               // …pero _ctrl.text no se actualiza
},
```

**Mejora sugerida:** Reasignar `_ctrl.text` cuando el valor cambia y preservar la posición del cursor:

```dart
onChanged: (v) {
  var n = int.tryParse(v) ?? 0;
  if (n < 0) n = 0;
  if (n > it.cantidadEntregada) n = it.cantidadEntregada;
  setState(() {
    it.cantidadRetornada = n;
    if (n.toString() != v) {
      _ctrl
        ..text = '$n'
        ..selection = TextSelection.collapsed(offset: '$n'.length);
    }
  });
},
```

#### 2. Flag `_chequeandoRetorno` asignado después de un `await` — carrera posible

**Archivo:** `e_zyro_app/lib/screens/pantalla_detalle_servicio.dart` — método `_verificarRetornoPendiente`

**Problema:** La bandera de reentrada se establece en `true` **después** del primer `await`, por lo que si la función es invocada dos veces antes de que el primer `await` devuelva (lo cual puede ocurrir si `_retornoService` es null: la llamada inicial de `_load` y un evento WS llegan casi simultáneamente), ambas pasan el guard inicial sin bloquearse mutuamente.

```dart
Future<void> _verificarRetornoPendiente() async {
  if (_chequeandoRetorno || !mounted) return;         // guard
  final svc = _retornoService ?? await getRetornoService();  // <-- await aquí
  _retornoService = svc;
  _chequeandoRetorno = true;   // <-- asignado DESPUÉS del await
```

Si `_retornoService` ya está inicializado (caso habitual), no hay `await` antes del flag y la carrera no ocurre. El riesgo es en la primera carga si el evento WS llega muy rápido.

**Mejora sugerida:** Mover el flag a `true` antes del primer `await`:

```dart
Future<void> _verificarRetornoPendiente() async {
  if (_chequeandoRetorno || !mounted) return;
  _chequeandoRetorno = true;   // proteger antes del await
  try {
    final svc = _retornoService ?? await getRetornoService();
    _retornoService = svc;
    final check = await svc.checkRetornoServicio(widget.servicioId);
    _chequeandoRetorno = false;
    ...
  } catch (_) {
    _chequeandoRetorno = false;
  }
}
```

#### 3. `canReachServer` crea un cliente HTTP nuevo en cada llamada

**Archivo:** `e_zyro_app/lib/services/proyecto_service.dart` — método `canReachServer`

**Problema:** Cada llamada abre y cierra un `http.Client()` dedicado solo para el ping de conectividad. En `sincronizarEvidencias`, si hay cola de evidencias pendientes, puede llamarse repetidamente. No hay fuga de recursos (el `finally` cierra el cliente), pero es innecesariamente costoso en términos de conexiones TCP.

**Mejora sugerida:** Reutilizar `_client` (la instancia de `ApiClient` ya disponible) para el ping, o al menos mantener un cliente `http.Client` de reachability a nivel de servicio. El patrón idéntico existe en `AsistenciaService.canReachServer` — si se centraliza, una sola versión bastaría para ambos servicios.
