#### 1. N+1 en `epp.py` — `anular_entrega` y `crear_ingreso`
**Archivos:** `BACKEND/app/routers/epp.py` (función `anular_entrega`, ~línea 264; función `crear_ingreso`, ~línea 411)

En `anular_entrega` se hace `db.query(Epp).filter(Epp.id == d.epp_id).first()` dentro de un loop sobre `detalles`, lo que genera una consulta SQL por cada ítem de la entrega. Lo mismo ocurre en `crear_ingreso` (`e = db.query(Epp).filter(Epp.id == it.epp_id).first()` dentro del loop). La función análoga `crear_entrega` ya tiene el patrón correcto (usa un diccionario `epps` precargado). Aplicar el mismo patrón:

```python
epp_ids = [d.epp_id for d in detalles]
epps = {str(e.id): e for e in db.query(Epp).filter(Epp.id.in_(epp_ids)).all()}
for d in detalles:
    e = epps.get(str(d.epp_id))
```

#### 4. Filtro `estado` aplicado en Python tras el `LIMIT` — `documentos_sst.py`
**Archivo:** `BACKEND/app/routers/documentos_sst.py` (función `listar`, ~línea 133)

```python
rows = qry.order_by(...).offset(offset).limit(limit).all()
...
if estado:
    out = [o for o in out if o.estado == estado]
```

El filtro `estado` (vigente/por\_vencer/vencida) se calcula con `date.today()` en Python y se aplica *después* de que SQL ya aplicó `LIMIT`. Resultado: pedir `estado=vencida&limit=100` puede devolver 0 resultados aunque existan documentos vencidos más allá del page. Lo correcto es convertir el filtro a SQL antes del `LIMIT`:

```python
if estado == "vencida":
    qry = qry.filter(DocumentoSst.fecha_vencimiento < date.today())
elif estado == "por_vencer":
    qry = qry.filter(
        DocumentoSst.fecha_vencimiento >= date.today(),
        DocumentoSst.fecha_vencimiento <= date.today() + timedelta(days=_DIAS_AVISO))
elif estado == "vigente":
    qry = qry.filter(DocumentoSst.fecha_vencimiento > date.today() + timedelta(days=_DIAS_AVISO))
elif estado == "sin_fecha":
    qry = qry.filter(DocumentoSst.fecha_vencimiento.is_(None))
```

#### 5. `Access-Control-Allow-Origin: *` en handler de 500 — exposición de información
**Archivo:** `BACKEND/app/main.py` (~línea 1732)

```python
headers={"Access-Control-Allow-Origin": "*"},
```

El handler global de excepciones no capturadas devuelve el tipo y mensaje de la excepción (`f"{type(exc).__name__}: {exc}"`) con cabecera `*`. Cualquier origen puede leer ese mensaje, que puede contener rutas de archivos, nombres de tabla, valores de parámetros u otra información interna. Recomendación: usar los mismos orígenes configurados en el middleware CORS (lista blanca), o al menos limitar el contenido del `detail` a un mensaje genérico.

#### 6. Segundo `db.commit()` fuera de control tras notificación — `rrhh_solicitudes.py`
**Archivo:** `BACKEND/app/routers/rrhh_solicitudes.py` (~línea 175)

```python
db.commit()          # commit principal de la evaluación
db.refresh(sol)

emp = db.query(Empleado)...
if emp:
    notificar_usuario(...)
    db.commit()      # segundo commit sin try/except
```

Si `notificar_usuario` escribe algo en la sesión y falla antes del segundo commit, la excepción burbujea y el cliente recibe un 500 aunque la evaluación principal ya se guardó. La notificación debería estar en su propio `try/except` para que un fallo de notificación no rompa la respuesta.

### Hallazgos

#### 1. Carga secuencial en `_init()` que podría ser paralela — `pantalla_documentos_sst.dart`
**Archivo:** `e_zyro_app/lib/screens/pantalla_documentos_sst.dart` (método `_init`, ~línea 46)

```dart
_svc = DocumentoSstService(ApiClient(prefs));
_clientes = await _svc!.getClientes();   // 1ª petición
await _cargar();                          // 2ª petición (getDocumentos)
```

Una vez que `_svc` está disponible, `getClientes()` y `getDocumentos()` son independientes. Ejecutarlos en secuencia duplica el tiempo de carga inicial. Mejora:

```dart
_svc = DocumentoSstService(ApiClient(prefs));
setState(() => _cargando = true);
final results = await Future.wait([
  _svc!.getClientes(),
  _svc!.getDocumentos(tipo: _filtroTipo, clienteId: _filtroCliente, q: _busqueda),
]);
if (!mounted) return;
setState(() {
  _clientes = results[0] as List<ClienteBasico>;
  _items    = results[1] as List<DocumentoSst>;
  _cargando = false;
});
```

#### 2. `NotificationService.initialize()` no condicionado al éxito de Firebase — `main.dart`
**Archivo:** `e_zyro_app/lib/main.dart` (~línea 60)

```dart
WidgetsBinding.instance.addPostFrameCallback((_) async {
  try {
    await Firebase.initializeApp();
    ...
  } catch (e) { ... }         // Firebase falla silenciosamente
  try {
    await NotificationService.initialize();  // se ejecuta igual
  } catch (e) { ... }
});
```

Si `Firebase.initializeApp()` falla, `NotificationService.initialize()` se ejecuta de todas formas, intentando usar FCM sin Firebase activo. Debería anidarse dentro del bloque try exitoso de Firebase, o al menos controlarse con una bandera:

```dart
bool firebaseOk = false;
try {
  await Firebase.initializeApp();
  firebaseOk = true;
} catch (e) { ... }
if (firebaseOk) {
  try { await NotificationService.initialize(); } catch (e) { ... }
}
```
