### Hallazgos

#### 1. Filtrado en memoria tras cargar todos los registros de BD
**Archivo:** `BACKEND/app/routers/operaciones.py` — función `get_proyectos` y `get_servicios_proyecto` (commit b91e3682)

Los parámetros `q` (búsqueda de texto) y `estado` se aplican en Python sobre la lista retornada por `.all()`, es decir, **después** de haber traído todos los proyectos/servicios de la base de datos. Para empresas con muchos registros esto carga datos innecesarios en memoria y CPU.

```python
# Ejemplo actual (get_proyectos):
rows = base_q.all()          # trae TODO a Python
if estado:
    rows = [r for r in rows if (r.Proyecto.estado or "") == estado]   # filtra en memoria
if q:
    rows = [r for r in rows if q_low in (r.Proyecto.nombre_proyecto or "").lower() ...]
```

**Mejora sugerida:** trasladar estos filtros a cláusulas `.filter()` de SQLAlchemy antes de llamar a `.all()`, de modo que el WHERE se ejecute en PostgreSQL:

```python
if estado:
    base_q = base_q.filter(Proyecto.estado == estado)
if q:
    ilike = f"%{q.strip()}%"
    base_q = base_q.filter(or_(Proyecto.nombre_proyecto.ilike(ilike), ...))
rows = base_q.all()
```

#### 2. Bug de acceso: Técnico con Tarea (sin ProyectoMiembro) ve el proyecto pero recibe 403 en sus servicios
**Archivo:** `BACKEND/app/routers/operaciones.py` — funciones `get_proyectos` y `get_servicios_proyecto` (commit d549fbff)

En `get_proyectos`, la visibilidad del Técnico se amplió a `ProyectoMiembro OR Tarea` (correcto). Pero en `get_servicios_proyecto`, el guard solo verifica `ProyectoMiembro` y la FK `jefe_operaciones_id`:

```python
# get_servicios_proyecto (commit d549fbff):
if es_tecnico(payload):
    es_jefe    = proyecto.jefe_operaciones_id == empleado.id
    es_miembro = db.query(ProyectoMiembro).filter(...).first() is not None
    if not es_jefe and not es_miembro:
        raise HTTPException(status_code=403, ...)  # ← un Técnico con Tarea cae aquí
```

Un Técnico asignado a una `Tarea` de un proyecto del que no es `ProyectoMiembro` aparece en el listado de proyectos, pero al intentar ver los servicios de ese proyecto recibe un 403 inconsistente.

**Mejora sugerida:** agregar una subquery de Tarea al check, igual que en `get_proyectos`:

```python
tiene_tarea = db.query(Tarea).filter(
    Tarea.proyecto_servicio_id.in_(
        db.query(ProyectoServicio.id).filter(ProyectoServicio.proyecto_id == proyecto_id)
    ),
    Tarea.responsable_id == empleado.id,
    Tarea.empresa_id     == empresa_id,
).first() is not None
if not es_jefe and not es_miembro and not tiene_tarea:
    raise HTTPException(status_code=403, ...)
```

#### 3. Consulta COUNT redundante en `get_detalle_servicio`
**Archivo:** `BACKEND/app/routers/operaciones.py` — función `get_detalle_servicio` (commit 39b71628)

Antes de cargar los procedimientos del servicio, se ejecuta una consulta `COUNT` extra:

```python
# ~línea 668:
sin_proc_estandar = bool(ps.catalogo_servicio_id) and not (
    db.query(func.count(Procedimiento.id))
    .filter(Procedimiento.proyecto_servicio_id == ps.id)
    .scalar()
)
```

Más adelante, una vez cargados los procedimientos en `procs`, se recalcula:

```python
# ~línea 813:
sin_proc_estandar = bool(ps.catalogo_servicio_id) and not procs
```

El COUNT inicial añade un round-trip innecesario a la BD en cada llamada al detalle de servicio que tenga `catalogo_servicio_id`. Dado que `procs` ya se carga a continuación, la primera verificación puede eliminarse y usar únicamente la recalculada con la lista en memoria.

### Hallazgos

#### 1. Bucle de paginación sin límite superior de páginas
**Archivo:** `e_zyro_app/lib/services/proyecto_service.dart` (commit 709a857e, alrededor de la línea 175)

```dart
do {
  final r = await _client.get(
    '/operaciones/proyecto/$proyectoId/servicios?page=$page&page_size=100',
  );
  if (r.statusCode != 200) break;
  // ...
  totalPages = (pag is Map ? pag['total_pages'] as int? : null) ?? 1;
  page++;
} while (page <= totalPages);  // ← sin cap máximo
```

Si el backend devuelve un `total_pages` inesperadamente grande (bug del API o respuesta malformada), la app realizará peticiones HTTP secuenciales indefinidamente, bloqueando al usuario y pudiendo agotar memoria/conexiones.

**Mejora sugerida:** añadir una guardia de seguridad:

```dart
} while (page <= totalPages && page <= 50); // cap de 5 000 ítems (50 × 100)
```

#### 2. Lista parcial devuelta sin advertencia al usuario si falla una página intermedia
**Archivo:** `e_zyro_app/lib/services/proyecto_service.dart` (commit 709a857e, alrededor de la línea 173)

El flag `ok` se establece a `true` tras la primera página exitosa. Si una página posterior falla (break por `statusCode != 200`), el método retorna los ítems acumulados hasta ese punto como si la carga fuera completa, sin que la UI lo indique:

```dart
var ok = false;
do {
  if (r.statusCode != 200) break;
  ok = true;    // ← se activa en page=1; si page=3 falla, ok sigue siendo true
  // ...
} while (...);
if (ok) {
  // devuelve all (posiblemente incompleto)
}
```

El usuario podría ver una lista truncada sin ningún aviso de que faltan servicios.

**Mejora sugerida:** distinguir el éxito total del parcial, por ejemplo con un flag `allPagesLoaded`, y en caso de carga incompleta mostrar un `SnackBar` de advertencia o caer en el caché offline.
