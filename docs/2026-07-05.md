### Hallazgos

#### H1 — Consultas N+1 en el listado de backups
**Archivo:** `BACKEND/app/routers/backups.py`, función `_out` (~línea 192) y `listar_backups` (~línea 266)

La función `_out` ejecuta `db.query(Usuario.nombre).filter(Usuario.id == j.disparado_por).first()` dentro de sí misma, y es llamada en una comprensión de lista por cada fila del resultado de `listar_backups`. Con `page_size` de hasta 100, esto produce hasta 100 queries extra por petición a `GET /backups`.

**Mejora sugerida:** Antes del loop, construir un diccionario de nombres en una sola consulta:
```python
ids = {j.disparado_por for j in rows if j.disparado_por}
nombres_map = {}
if ids:
    for uid, nombre in db.query(Usuario.id, Usuario.nombre).filter(Usuario.id.in_(ids)):
        nombres_map[uid] = nombre
```
Y pasar `nombres_map` a una versión de `_out` que lo reciba como parámetro.

#### H2 — Descargas de Cloudinary completamente secuenciales
**Archivo:** `BACKEND/app/services/backup_service.py`, función `_empaquetar_archivos` (~línea 501)

El bucle descarga cada recurso de Cloudinary uno por uno con `requests.get(url, stream=True)`. En un backup full semanal con cientos o miles de archivos, el tiempo total de ejecución es la suma de todas las latencias individuales (potencialmente decenas de minutos).

**Mejora sugerida:** Paralelizar con un pool acotado para no saturar la red ni agotar los file descriptors:
```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def _descargar_uno(r, tmp_path):
    url = r.get("secure_url")
    if not url:
        r["error"] = "sin secure_url"
        return r
    ext = f".{r['format']}" if r.get("format") else ""
    nombre = r["public_id"].replace("/", "__") + ext
    try:
        with requests.get(url, stream=True, timeout=120) as resp:
            resp.raise_for_status()
            with open(tmp_path / nombre, "wb") as f:
                for chunk in resp.iter_content(1024 * 256):
                    f.write(chunk)
        r["archivo_en_tar"] = nombre
    except Exception as e:
        r["error"] = str(e)[:300]
    return r

with ThreadPoolExecutor(max_workers=8) as ex:
    futures = [ex.submit(_descargar_uno, r, tmp_path) for r in recursos]
    recursos = [f.result() for f in as_completed(futures)]
empaquetados = sum(1 for r in recursos if "archivo_en_tar" in r)
```

#### H3 — Condición de carrera (TOCTOU) en backup manual
**Archivo:** `BACKEND/app/routers/backups.py`, endpoint `POST /backups` (~línea 230)

La comprobación de si ya hay un backup manual en curso y la creación del nuevo job son dos operaciones separadas sin ningún mecanismo de exclusión mutua a nivel de base de datos. Si dos peticiones HTTP llegan en el mismo milisegundo, ambas pueden pasar el `if activo: raise HTTPException(409)` y lanzar dos hilos de backup simultáneos.

**Mejora sugerida:** Usar un partial unique index en PostgreSQL sobre la tabla `backup_job`:
```sql
CREATE UNIQUE INDEX IF NOT EXISTS uix_backup_manual_activo
  ON backup_job (tipo)
  WHERE tipo = 'manual' AND estado IN ('pendiente', 'en_proceso');
```
Así la BD rechaza el segundo insert con `IntegrityError` y el router lo captura devolviendo 409, sin importar la concurrencia a nivel de Python.

#### H4 — Consultas N+1 en `_nombre_detalle` al notificar ítems rechazados
**Archivo:** `BACKEND/app/routers/logistica.py`, función `_nombre_detalle` y su llamada (~línea 1838)

```python
nombres_rechazados = [_nombre_detalle(db, d) for d in detalles if d.estado_item == "rechazado"]
```

Cada llamada a `_nombre_detalle` ejecuta `db.query(Material.nombre)...` o `db.query(Equipo.nombre)...` para resolver el nombre del ítem. Para N ítems rechazados, son N queries extras en el mismo request de aprobación.

Este endpoint ya tiene muchas operaciones de BD; en un requerimiento grande con varios rechazos el impacto es perceptible. **Mejora:** Pre-cargar en batch todos los materiales/equipos referenciados por los detalles rechazados con `WHERE id IN (...)` antes del loop.
