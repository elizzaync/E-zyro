# Resumen y revisión de código — 2026-06-18

## Backend (`branch: Backend / carpeta: BACKEND/`)

### Resumen de lo trabajado

Jornada con 19 commits. Los cambios principales abarcan:

- **WebSocket de soporte en tiempo real** (`soporte_ws.py`, `main.py`): Nuevo router que emite eventos de tickets, sesiones activas, IPs y dispositivos a los clientes conectados mediante WebSocket.
- **Token con TTL por plataforma** (`auth.py`): El token de acceso dura 7 días para la app móvil y 4 horas para la web. La detección se realiza por el campo `platform` o por el User-Agent. Incluye lógica de `refresh_token` que calcula la duración original de la sesión.
- **Seguridad — IP blocklist y middleware** (`main.py`, `soporte.py`): Middleware `IpBlockMiddleware` que consulta la tabla `ip_bloqueada` en cada request; endpoints para gestionar IPs bloqueadas, listar sesiones activas por empresa, y cerrar sesiones remotas.
- **Seguridad — reportes de dispositivos y auditoría** (`soporte.py`, `auditoria.py`): Endpoint `reporte_dispositivos` que agrupa sesiones por usuario; endpoint `revertir_registro` en auditoría que reconstruye un `UPDATE` dinámico sobre la tabla afectada.
- **Asistencia/RRHH — justificación de tardanza** (`permisos.py`): Nuevo endpoint `justificar_tardanza` que crea una solicitud de tipo `justificacion_tardanza` con campos de minutos y tipo de justificación.
- **Asistencia — resumen semanal personal** (`rrhh_asistencia.py`): Endpoint `mi-resumen-semanal` que devuelve el resumen de marcaciones de la semana en curso para el empleado autenticado.
- **Garantías y portal cliente** (`operaciones.py`, `portal_cliente.py`): Carta de Garantía integrada al portal del cliente; generación de informe general interno con subida a Cloudinary.
- **Equipos Intervenidos** (`operaciones.py`): Nuevo vínculo a la inspección anterior (`inspeccion_padre_id`) y sección "servicio actual" en el endpoint de inspección activa.
- **Legajo / RRHH** (`rrhh_legajo.py`, empleados): Campo CUSPP en el modelo de empleado, fórmulas salariales legales (AFP, ONP, CTS, etc.) y endpoint PATCH para actualizar perfil de legajo.
- **PDF / Pozo** (`pdf_certificados.py`): Tres commits de fix: centrado de textos en celdas, posición del campo `CERTIFICADO`, auto-llenado de N° de Pozo; actualización de la plantilla base.

### Hallazgos

#### 1. `TypeError` en `refresh_token` por mezcla de datetimes aware/naive
**Archivo:** `BACKEND/app/routers/auth.py` — función `refresh_token` (~línea 565-567)

La duración original de la sesión se calcula como `sesion.fecha_expiracion - sesion.created_at`. `fecha_expiracion` se almacena con `datetime.now(ZONA_HORARIA)` (timezone-aware, America/Lima) mientras que `created_at` se almacena con `datetime.utcnow()` (naive). Restar un datetime aware con uno naive lanza `TypeError` en Python 3; el fallback `else ACCESS_TOKEN_EXPIRE_MINUTES` no lo captura porque no hay `try/except`.

**Sugerencia:** Normalizar antes de restar: `sesion.fecha_expiracion.replace(tzinfo=None) - sesion.created_at`, o bien guardar `fecha_expiracion` con `datetime.utcnow()` de forma consistente en toda la aplicación.

#### 2. Inyección SQL en `revertir_registro` (auditoría)
**Archivo:** `BACKEND/app/routers/auditoria.py` — función `revertir_registro` (~línea 214-247)

El nombre de tabla (`tabla = str(registro.tabla_afectada)`) se inserta directamente en el SQL con f-string: `f'UPDATE "{tabla}" SET {set_parts} WHERE id = :_reg_id'`. Los valores de columnas van como parámetros bindados, pero el nombre de tabla no. Si un atacante corrompiera el campo `tabla_afectada` en un registro de auditoría (mediante otra vulnerabilidad), podría ejecutar SQL arbitrario.

**Sugerencia:** Validar `tabla` contra una lista blanca antes de construir el SQL:
```python
TABLAS_REVERTIBLES = {"usuario", "empleado", ...}
if tabla not in TABLAS_REVERTIBLES:
    raise HTTPException(400, "Tabla no permitida")
```

#### 3. N+1 queries en `reporte_dispositivos`
**Archivo:** `BACKEND/app/routers/soporte.py` — función `reporte_dispositivos` (~líneas 755-800)

Por cada grupo de sesiones el endpoint hace `db.query(Usuario).filter(Usuario.id == usuario_id_str).first()` dentro del bucle, generando una query por usuario. Con 50 usuarios activos se ejecutan 50 queries adicionales.

**Sugerencia:** Construir el dict de usuarios antes del bucle con una sola query:
```python
ids = list(grupos.keys())
usuarios_map = {str(u.id): u for u in db.query(Usuario).filter(Usuario.id.in_(ids)).all()}
```

---

#### 4. N+1 queries en `listar_sesiones` / `sesiones_activas`
**Archivo:** `BACKEND/app/routers/soporte.py` — función `listar_sesiones` (~línea 89) y `sesiones_activas` (~línea 758)

La función auxiliar `_nombre_usuario(db, s.usuario_id)` se llama dentro del bucle de resultados paginados, ejecutando una query a `Usuario` por cada sesión. Con `page_size=50` son hasta 50 queries adicionales por página.

**Sugerencia:** Recolectar los IDs únicos de la página, hacer `db.query(Usuario).filter(Usuario.id.in_(...))`, y resolver nombres desde un dict local.

---

#### 5. N+1 queries anidadas en `get_inspeccion_activa` (Equipos Intervenidos)
**Archivo:** `BACKEND/app/routers/operaciones.py` — función `get_inspeccion_activa` (~líneas 4288-4305 y 4359-4375)

Cuando una inspección tiene `inspeccion_padre_id`, se lanza `db.query(HistorialInspeccion).filter(...).first()` como query separada, y dentro de `_resumen_vinculo` se lanza otra para obtener el `ProyectoServicio` del padre. Esto suma hasta 3 queries extra por inspección con padre.

**Sugerencia:** Incluir el padre con eager loading en la query principal (`joinedload(HistorialInspeccion.padre)`) y resolver el `ProyectoServicio` en el mismo JOIN.

---

#### 6. Middleware de IP blocklist no filtra por `empresa_id` y consulta BD en cada request
**Archivo:** `BACKEND/app/main.py` — clase `IpBlockMiddleware.dispatch` (~líneas 1815-1820)

El middleware bloquea una IP a nivel global: si la empresa A bloquea la IP 1.2.3.4, queda bloqueada para todas las empresas del sistema (ignora la columna `empresa_id` de `IpBloqueada`). Además, abre una conexión nueva a la BD por cada request HTTP, incluyendo los no autenticados, lo que puede agotar el pool bajo carga.

**Sugerencia:** Mover la verificación de IP bloqueada a una dependencia FastAPI que se ejecute después de verificar el token (donde ya se conoce `empresa_id`). Para reducir la presión sobre la BD, mantener un `set` en memoria con TTL corto (≈30 s) de IPs bloqueadas por empresa.

---

#### 7. Import de router `soporte_ws` fuera de la sección de imports
**Archivo:** `BACKEND/app/main.py` (~línea 1922)

La importación `from app.routers import soporte_ws as soporte_ws_module` se realiza dentro del cuerpo del módulo, en medio del bloque de registro de routers, en lugar de la sección de imports del principio. No produce un error funcional pero viola el patrón del resto del archivo y puede confundir linters.

**Sugerencia:** Mover la importación a la cabecera de `main.py` junto al resto de los routers.

---

#### 8. Sockets muertos no se limpian en `_broadcast` del WebSocket manager
**Archivo:** `BACKEND/app/routers/soporte_ws.py` — método `_broadcast` (~línea 130)

El lock se adquiere para copiar la lista de sockets y se libera antes de iterar y enviar. Si un socket está desconectado, la excepción de `send_text` se captura silenciosamente pero el socket permanece en `self._conns` hasta que el cliente llame a `ws.receive_text()` y genere `WebSocketDisconnect`. Los sockets muertos se acumulan.

**Sugerencia:** Registrar los sockets que fallaron durante el broadcast y eliminarlos de `self._conns` al finalizar el envío.

---

#### 9. `fecha_expiracion` de Cloudinary en portal cliente sin índice efectivo
**Archivo:** `BACKEND/app/routers/portal_cliente.py` — función `portal_documentos` (~líneas 476-489)

La query de cartas de garantía usa `cg.empresa_id::text = :eid` (cast explícito a texto en SQL raw). Este cast impide que PostgreSQL utilice índices sobre la columna `empresa_id` si es de tipo UUID nativo.

**Sugerencia:** Castear el parámetro en lugar de la columna: `cg.empresa_id = :eid::uuid`, permitiendo el uso de índices existentes.

---

#### 10. Campo `minutos_tarde` sin validación de rango en `justificar_tardanza`
**Archivo:** `BACKEND/app/routers/permisos.py` — función `justificar_tardanza` (~líneas 87-90)

El endpoint acepta `minutos_tarde` del body sin validar que sea positivo ni que tenga un límite razonable. Un cliente podría enviar `minutos_tarde: -999` o `minutos_tarde: 99999` y se guardaría sin rechazo.

**Sugerencia:** Agregar validación Pydantic en el schema de entrada (`ge=0, le=480`) o una comprobación explícita en el handler.

---

#### 11. Campo `fecha` opcional permite múltiples justificaciones sin fecha en `justificar_tardanza`
**Archivo:** `BACKEND/app/routers/permisos.py` — función `justificar_tardanza` (~línea 99)

Si el body no incluye `fecha` o el formato es inválido, `fecha_dt` es `None`, el check de duplicados se omite y se crea la solicitud con `fecha_inicio=None`. Esto permite enviar múltiples justificaciones sin fecha para el mismo empleado sin que el sistema lo detecte.

**Sugerencia:** Hacer `fecha` obligatorio en el schema de entrada o agregar `if not fecha_dt: raise HTTPException(422, "Se requiere una fecha válida YYYY-MM-DD")`.

---

#### 12. Orden incorrecto de validaciones en `revertir_registro`
**Archivo:** `BACKEND/app/routers/auditoria.py` — función `revertir_registro` (~línea 203)

El endpoint verifica primero el permiso `AUDITORIA:VER` y luego el rol admin. Un usuario con ese permiso pero sin rol admin pasa la primera verificación y recibe el error 403 del rol, revelando que el endpoint existe y requiere rol admin.

**Sugerencia:** Invertir el orden: verificar rol admin primero; si no lo tiene, retornar 403 genérico antes de evaluar permisos específicos.

## e-zyro-app (`branch: e-zyro-app / carpeta: e_zyro_app/`)

### Resumen de lo trabajado

Jornada con 6 commits. Los cambios principales abarcan:

- **Perfil unificado** (`pantalla_mi_espacio.dart`): Se fusionaron las pantallas "Mi Perfil" y "Mi espacio" en una única pantalla "Mi perfil" que incluye las últimas marcaciones del empleado.
- **Login móvil** (`auth_service.dart` o equivalente): El login desde la app envía `platform='movil'` para recibir un token de 7 días.
- **Hub RRHH** (nueva pantalla hub): Se unificó el acceso a las funcionalidades de RRHH del trabajador en un hub central.
- **Justificación de tardanza** (`pantalla_asistencia.dart`): Nueva sección en la pantalla de asistencia para que el trabajador justifique tardanzas, con bandeja de revisión.
- **Rediseño de Asistencia** (`pantalla_asistencia.dart`): Pantalla reorganizada con sección de Reportes e historial por día expandible, usando `Future.wait` para cargas paralelas.
- **Equipos Intervenidos** (pantalla de inspección): Nueva sección "En este servicio" con selector del servicio anterior vinculado.

### Hallazgos

#### 1. Descarga completa del historial para mostrar solo 6 registros
**Archivo:** `e_zyro_app/lib/screens/pantalla_mi_espacio.dart` — método `_cargar` (~líneas 37-45)

Se llama `asis.getHistorial()` sin límite y luego se aplica `.take(6)` en el cliente. Si el usuario tiene meses de historial, se descarga toda la lista del servidor para mostrar únicamente 6 filas, desperdiciando ancho de banda y aumentando el tiempo de carga.

**Sugerencia:** Si el endpoint `/asistencia/historial` acepta `limit`, pasar `limit=6` desde el cliente. Si no lo acepta, agregarlo en el backend.

---

#### 2. Llamadas a API secuenciales donde deberían ser paralelas
**Archivo:** `e_zyro_app/lib/screens/pantalla_mi_espacio.dart` — método `_cargar` (~línea 37)

Las tres llamadas a la API (`getResumenSemanal`, `misSolicitudes`, `getHistorial`) se ejecutan con `await` secuencial. Cada una espera a que la anterior termine, triplicando el tiempo de carga percibido.

**Sugerencia:** Usar `Future.wait`:
```dart
final results = await Future.wait([
  asis.getResumenSemanal(),
  solSvc.misSolicitudes(),
  asis.getHistorial(),
]);
```

---

#### 3. Descarga de todas las solicitudes para filtrar por tipo en pantalla de asistencia
**Archivo:** `e_zyro_app/lib/screens/pantalla_asistencia.dart` — método `_cargarJustificaciones` (~líneas 130-137)

`_cargarJustificaciones()` llama a `_solSvc!.misSolicitudes()` que descarga todas las solicitudes laborales del trabajador y luego filtra en cliente las de tipo `justificacion_tardanza`. Si el trabajador tiene muchos registros históricos, se transfieren datos innecesarios. Además, esta misma llamada se repite en `pantalla_mi_espacio.dart`, duplicando el request de red si ambas pantallas están activas.

**Sugerencia:** Agregar un parámetro de filtro al endpoint: `/permisos/mis-solicitudes?tipo=justificacion_tardanza`, y pasar ese parámetro desde el cliente.

---

#### 4. Riesgo de `setState` tras desmontaje en `_abrirJustificarTardanza`
**Archivo:** `e_zyro_app/lib/screens/pantalla_asistencia.dart` — cierre dentro de `_abrirJustificarTardanza` (~línea 290)

Tras un envío exitoso, se llama `await _cargarJustificaciones()` desde dentro del closure del `showModalBottomSheet`. Si el widget se destruye durante el `await` (el usuario navega hacia atrás), puede producirse un `setState` sobre un widget desmontado, generando una advertencia o crash en modo debug.

**Sugerencia:** Agregar `if (!mounted) return;` inmediatamente después del `await _cargarJustificaciones()` en el sitio de llamada dentro del callback.

---

#### 5. `Future.wait` sin manejo de errores parciales en `_cargarDatos`
**Archivo:** `e_zyro_app/lib/screens/pantalla_asistencia.dart` — método `_cargarDatos` (~líneas 193-202)

Los resultados de `Future.wait` se indexan como `results[0]`, `results[1]`, `results[2]`. Si cualquiera de los tres futures lanza una excepción, `Future.wait` propaga el primer error y los demás resultados se pierden; la pantalla queda en estado de carga indefinida. Además, el cast `results[2] as ResumenSemanal?` puede fallar si el tipo real no coincide.

**Sugerencia:** Envolver cada future en un `catchError` o usar `eagerError: false` en `Future.wait`, y manejar el estado de error parcial en la UI para que los datos disponibles sí se muestren.
