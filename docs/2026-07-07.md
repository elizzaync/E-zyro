### Hallazgos

#### 1. Almuerzo post-turno no se descuenta de las horas extra (bug potencial)
**Archivo:** `BACKEND/app/services/planilla_asistencia_service.py`
**Commit:** `f249c42d`
**Línea aprox.:** función `_horas_dia_ancladas`, sentencia `horas_extra_bruto = max(0.0, (salida - turno_salida_dt).total_seconds() / 3600.0)`

El cálculo de `horas_extra_bruto` usa el span crudo `(salida − turno_hora_salida)` sin descontar el tiempo de almuerzo que pudiera caer después de la hora de salida pactada. Si un empleado empieza su almuerzo a las 18:15 (después de la salida del turno a las 18:00) y vuelve a las 19:00, el sistema contará 60 minutos de sobretiempo cuando en realidad son 0 minutos de trabajo real extra. El bloque de deducción de almuerzo que existe para las horas regulares no se aplica a `horas_extra_bruto`.

**Sugerencia:** Después de calcular `horas_extra_bruto`, descontar el tiempo de almuerzo que caiga en el tramo `[turno_salida_dt, salida]`:
```python
if ini_alm and fin_alm and fin_alm > ini_alm:
    alm_extra_ini = max(ini_alm, turno_salida_dt)
    alm_extra_fin = min(fin_alm, salida)
    if alm_extra_fin > alm_extra_ini:
        horas_extra_bruto -= (alm_extra_fin - alm_extra_ini).total_seconds() / 3600.0
horas_extra_bruto = max(0.0, horas_extra_bruto)
```

#### 2. Lista completa de registros escaneada por día en el loop interno (ineficiencia)
**Archivo:** `BACKEND/app/services/planilla_asistencia_service.py`
**Commit:** `e1ec9aa2`
**Línea aprox.:** dentro del loop `for dia in todos_los_dias:` — sentencia `regs_dia = [r for r in regs if r.fecha_hora.date() == dia]`

Para cada empleado y cada día del período, se hace una búsqueda lineal sobre la lista completa de registros de ese empleado. Con 30 días y ~120 registros/empleado (4 tipos × 30 días) son 3.600 comparaciones por empleado; con 100 empleados, 360.000. El problema crece linealmente con el período.

**Sugerencia:** Pre-agrupar `regs` por fecha antes del loop de días:
```python
regs_por_dia: dict[date, list] = {}
for r in regs:
    regs_por_dia.setdefault(r.fecha_hora.date(), []).append(r)
```
Luego en el loop: `regs_dia = regs_por_dia.get(dia, [])` — acceso O(1) en lugar de O(n).

#### 3. Notificación a Jefes carga todos los usuarios en Python (ineficiencia)
**Archivo:** `BACKEND/app/routers/operaciones.py`
**Commit:** `aefb9411`
**Línea aprox.:** función `_notificar_servicio_pendiente_a_jefes`, query `.filter(Usuario.empresa_id == empresa_id, Usuario.activo == True)`

La consulta trae todos los usuarios activos de la empresa junto con sus roles, y el filtro `"jefe" in _norm_rol(rnombre) and "operac" in _norm_rol(rnombre)` se aplica en Python. En empresas con cientos de empleados esto carga filas innecesarias. El filtro debería empujarse a la BD.

**Sugerencia:** Agregar al query:
```python
.filter(Rol.nombre.ilike('%jefe%'), Rol.nombre.ilike('%operac%'))
```
O usar un filtro de rol exacto si el nombre está estandarizado en el sistema.

### Hallazgos

#### 1. Agrupación por zona recalculada en cada frame de scroll (ineficiencia)
**Archivo:** `e_zyro_app/lib/screens/pantalla_equipos_intervenidos.dart`
**Commit:** `e3e6cbd8`
**Línea aprox.:** método `_parqueView`, bloque `itemBuilder: (_, i) { ... final porZona = <String, List<EquipoIntervenido>>{}; for (final e in equipos) { ... } }`

El `porZona` se construye dentro de `itemBuilder`, lo que significa que se recalcula en cada frame de layout mientras el usuario hace scroll. Flutter puede invocar `itemBuilder` docenas de veces por segundo durante el desplazamiento.

**Sugerencia:** Mover la agrupación fuera del builder, junto a donde ya se construye `porUbicacion`:
```dart
// En _parqueView, antes de return ListView.builder:
final porZonaMap = <String, Map<String, List<EquipoIntervenido>>>{};
for (final entry in porUbicacion.entries) {
  final byZona = <String, List<EquipoIntervenido>>{};
  for (final e in entry.value) {
    byZona.putIfAbsent(e.zonaNombre ?? 'Sin zona', () => []).add(e);
  }
  porZonaMap[entry.key] = byZona;
}
// En itemBuilder:
final porZona = porZonaMap[ubic]!;
```

#### 2. Listener del TabController dispara setState en cada frame de animación (ineficiencia)
**Archivo:** `e_zyro_app/lib/screens/pantalla_plantillas_procedimiento.dart`
**Commit:** `c0dcbf9b`
**Línea aprox.:** `initState` — `_tabCtrl = TabController(length: 2, vsync: this)..addListener(() => setState(() {}));`

El `addListener` ejecuta `setState(() {})` en cada tick de la animación de transición entre tabs (no solo al completarse), causando rebuilds repetidos del `Scaffold` completo durante cada cambio de pestaña.

**Sugerencia:** Filtrar dentro del listener para reconstruir solo cuando la animación haya finalizado:
```dart
_tabCtrl = TabController(length: 2, vsync: this)
  ..addListener(() {
    if (_tabCtrl.indexIsChanging) return;
    setState(() {});
  });
```
