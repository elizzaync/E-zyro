## Backend

### Resumen del trabajo
Día concentrado en tres frentes dentro de `BACKEND/`: la **Carta de Garantía de Servicio**, la **generación de certificados PDF** (Pozo a Tierra y Operatividad de Tableros) y ajustes de cabeceras/diseño en los documentos Word.

- **Carta de Garantía** (`56cd5b9c`, `05e74e0`, `2c85cc8`, `5f15274`): se crea `BACKEND/app/services/word_carta_garantia.py` (genera el `.docx` con `python-docx`), se persiste un registro en la tabla `carta_garantia` (nuevo modelo `CartaGarantia`, migración `add_carta_garantia_firma_urls.sql` que agrega `firma_verificador_url`, `firma_gerente_url`, `documento_pdf_url`), y se resuelve la **Razón Social** automáticamente desde BD (equipo intervenido → cliente, con *fallback* a proyecto → cliente y finalmente al payload del frontend). El header del documento pasó por varias iteraciones de diseño (tabla con celdas, tab-stops, e imágenes flotantes vía `wp:anchor`).
- **Firmas en Cloudinary** (`2bfcbd4`): las firmas (verificador/gerente) ahora se suben a Cloudinary (`folder=e-zyro/firmas/garantia`) reutilizando `subir_imagen_cloudinary()`, guardando las URLs resultantes; si Cloudinary falla, solo se registra un *warning* y el flujo continúa con base64 (resiliente).
- **Header con imágenes flotantes** (`c385eff`, `3b774f5`): se reemplaza el enfoque de tab-stops/sangría negativa por `wp:anchor` con `behindDoc=1` y coordenadas absolutas de página, para lograr compatibilidad entre Word y LibreOffice en `word_carta_garantia.py` y `word_informe_pozos.py`.
- **Certificados PDF** (`87cfa51`, `0d228ed`, `bcb6f28`): se crea `BACKEND/app/services/pdf_certificados.py` (inyección de campos sobre plantillas PDF existentes con PyMuPDF/`fitz`) y dos endpoints nuevos `POST /servicio/{id}/equipos-intervenidos/{eiId}/certificado/pozo` y `.../certificado/operatividad`, ambos validando que `estado_intervencion == 'completado'`. Se agregó `pymupdf` a `requirements.txt` y los assets `Certificado_Operatividad.pdf` / `Protocolo_Pozo_444.pdf`. Iteraciones posteriores agregaron `Body(default={})`, logging de diagnóstico y, finalmente, un nuevo set de campos para el protocolo de pozo (numero_pozo, fechas, fotos de procedimientos, firma del técnico).
- **Fix de estado de inspección** (`8708a9a`): se corrige un bug donde volver a llamar `GET /inspeccion` sobre un equipo ya `completado` creaba una nueva sesión `en_proceso` y reseteaba el estado, bloqueando la generación del certificado; ahora el endpoint detecta el estado `completado` y devuelve la última inspección sin modificarlo. Además `finalizar_inspeccion` ahora actualiza `ultimo_mantenimiento` y `proximo_mantenimiento` del equipo.
- **Informe general multi-tipo** (`a4c15dd`, `7584437`): se crea `BACKEND/app/services/report_templates.py` (~926 líneas, diccionarios de contenido por tipo de equipo: pozos, tableros, luminarias, pararrayos, UPS, transformador, combinados) y se generaliza `word_informe_pozos.py`/`generar_informe_general` para usar `cfg` según el tipo de equipo detectado (`get_config`/`_tipo_from_equipos`).

### Hallazgos

- **`BACKEND/app/routers/operaciones.py:4409-4411` (commit `2c85cc8`) — posible IDOR / fuga entre empresas (bug de seguridad)**: al resolver la Razón Social para la carta de garantía, se eliminó el filtro `EquipoIntervenido.empresa_id == empresa_id` de la consulta (`db.query(EquipoIntervenido).filter(EquipoIntervenido.id == first_ei_id)`), dejando solo el filtro por `id`. El comentario que lo justifica (línea 4401: *"la seguridad ya está garantizada por el check de ProyectoServicio de arriba"*) es incorrecto: `first_ei_id = equipos[0].get("id")` proviene directamente del payload del cliente y nunca se valida contra el `servicio_id`/`empresa_id` de la sesión. Un usuario autenticado de una empresa podría enviar el `id` de un `EquipoIntervenido` de **otra** empresa y obtener la `razón social` de un cliente ajeno en el documento generado. Sugerencia: restaurar el filtro `EquipoIntervenido.empresa_id == empresa_id`, o validar explícitamente que el equipo pertenezca al `servicio_id` recibido.

- **`BACKEND/app/services/pdf_certificados.py:21` (commit `87cfa51`) — ruta de assets dependiente del directorio de trabajo**: `_ASSETS = os.path.abspath("assets")` (igual que `_LOGO_HEADER`/`_DESIGN_HEADER` en `word_carta_garantia.py:21-22`) resuelve la ruta de las plantillas PDF de forma relativa al CWD del proceso. El propio código de `word_informe_pozos.py` documenta que esto "funciona porque en Docker el entrypoint corre desde `/app/`" — exactamente el mismo patrón que el día anterior (2026-06-06) ya había causado tres commits de *fix* por una ruta de logo rota en producción. Si el proceso se inicia desde otro directorio (tests, *workers*, otro entrypoint), `generar_protocolo_pozo`/`generar_certificado_operatividad` fallarán con `FileNotFoundError`/`fitz` no encontrará la plantilla. Sugerencia: resolver con `os.path.join(os.path.dirname(__file__), "..", "..", "assets", ...)` para independizar la ruta del CWD.

- **`BACKEND/app/services/word_carta_garantia.py:35-83` y `BACKEND/app/services/word_informe_pozos.py:50-98` (commit `c385eff`) — código duplicado**: la función `_add_floating_picture` (≈50 líneas, incluidas las constantes de namespace `_WP_NS`/`_A_NS`/`_W_NS` y la construcción manual del XML `wp:anchor`) se copió de forma idéntica en ambos servicios de generación de Word. Cualquier corrección futura del posicionamiento OOXML deberá replicarse manualmente en los dos archivos. Sugerencia: extraer este helper (junto con los de tablas como `_no_borders`, `_set_cell_bg`, etc., que también se repiten) a un módulo común, p. ej. `BACKEND/app/services/docx_utils.py`.

- **`BACKEND/app/routers/operaciones.py:4609-4612` (commit `0d228ed`) — logging de datos potencialmente sensibles**: el `logger.info` agregado para diagnosticar el endpoint de certificado de operatividad registra a nivel `INFO` campos como `nombre_tablero`, `razon_social`, `ubicacion` y `personal_tecnico` (datos de clientes/personas). Si los logs se centralizan o se conservan por mucho tiempo, esto expone información que debería tratarse como dato personal/de cliente. Sugerencia: bajar el nivel a `DEBUG` o registrar solo identificadores (`ei_id`, `empresa_id`) sin los valores de texto libre.
