### Hallazgos

#### 1. Dos consultas + filtro Python en lugar de un NOT IN SQL — `routers/cuentas_por_cobrar.py` (~líneas 121-149, commit `cec07fa0`)

**Problema:** `servicios_facturables` ejecuta primero una consulta para obtener los IDs ya facturados y los carga en un `set` Python; luego recupera **todos** los servicios Completados de la empresa y los filtra en Python con `if str(ps.id) in facturados`. Si la empresa tiene muchos servicios completados (cientos), todos se cargan en memoria antes de filtrar.

```python
# actual: dos round-trips + filtro Python
facturados = {str(sid) for (sid,) in db.query(FacturaCliente.proyecto_servicio_id).filter(...).all()}
filas = db.query(ProyectoServicio, ...).filter(...).all()
for ps, proy, cli in filas:
    if str(ps.id) in facturados:   # filtro en Python
        continue
```

**Mejora sugerida:** usar una subconsulta SQL para excluir los ya facturados en la propia query, eliminando el set Python y un round-trip:

```python
subq = db.query(FacturaCliente.proyecto_servicio_id).filter(
    FacturaCliente.empresa_id == empresa_id,
    FacturaCliente.proyecto_servicio_id.isnot(None),
    FacturaCliente.estado != "anulada",
).subquery()

filas = (
    db.query(ProyectoServicio, Proyecto, Cliente)
    .join(Proyecto, ...)
    .outerjoin(Cliente, ...)
    .filter(
        ProyectoServicio.empresa_id == empresa_id,
        ProyectoServicio.estado == "Completado",
        ProyectoServicio.id.notin_(subq),
    )
    .order_by(ProyectoServicio.updated_at.desc())
    .all()
)
```

#### 2. Patrón N+1: una consulta por día laborable — `services/planilla_asistencia_service.py` (líneas 52-79, commit `9861690e`)

**Problema:** `resumen_asistencia_periodo` itera sobre cada día laborable del periodo y llama `_resumen_dia(db, empresa_id, dia)` por cada uno. Para un mes de 23 días laborables, eso equivale a **~23 consultas** a la base de datos en secuencia. A medida que crezca el número de empleados el costo de cada llamada a `_resumen_dia` también sube.

```python
for dia in dias:                           # ~23 iteraciones
    resumen = _resumen_dia(db, empresa_id, dia)   # DB query por cada día
    for it in resumen.get("items", []):
        ...
```

**Mejora sugerida:** si `_resumen_dia` puede refactorizarse (o si se agrega una función `_resumen_rango`) para aceptar un rango de fechas y devolver todos los registros de asistencia en una sola query, el costo se reduce a 1 consulta. Como cambio menor sin tocar `_resumen_dia`, se puede al menos hacer las consultas en paralelo usando `asyncio.gather` si el router lo permite.

#### 3. Bug: `minutos_jornada` se sobreescribe en cada día, sobrevive solo el último valor — `services/planilla_asistencia_service.py` (líneas 63-66, commit `9861690e`)

**Problema:** dentro del bucle diario, `minutos_jornada` se actualiza con el valor de `minutos_requeridos` de cada día siempre que sea > 0. Para un empleado con turno consistente esto no importa, pero si la tolerancia o la duración del turno varía en algún día (o si hay días sin marca pero con turno), el acumulador toma el valor del **último día procesado** con turno no nulo en lugar de un valor representativo.

```python
mj = int(it.get("minutos_requeridos") or 0)
if mj > 0:
    a["minutos_jornada"] = mj   # sobreescribe; gana el último día
```

Esto afecta directamente el cálculo de descuento por tardanza en `planilla_service.py`:

```python
m = _d(valor_dia * Decimal(res["minutos_tardanza"]) / Decimal(res["minutos_jornada"]))
```

**Mejora sugerida:** acumular el valor más frecuente (moda) o simplemente fijarlo en la primera lectura y no sobreescribir:

```python
if mj > 0 and a["minutos_jornada"] == 0:
    a["minutos_jornada"] = mj   # se fija con el primer día válido
```

#### 4. `_recompute_planilla` carga todos los objetos boleta para sumar — `services/planilla_service.py` (líneas ~260-264, commit `9861690e`)

**Problema:** `_recompute_planilla` carga todos los objetos `BoletaPago` de la planilla en memoria para sumar sus totales con Python. Con 50+ empleados se trae un objeto completo por boleta solo para acceder a tres campos numéricos.

```python
bs = db.query(BoletaPago).filter(BoletaPago.planilla_id == planilla.id).all()
planilla.total_ingresos = sum((_d(b.total_ingresos) for b in bs), CERO)
```

**Mejora sugerida:** usar agregación SQL:

```python
from sqlalchemy import func
row = db.query(
    func.sum(BoletaPago.total_ingresos),
    func.sum(BoletaPago.total_descuentos),
    func.sum(BoletaPago.total_aportes),
).filter(BoletaPago.planilla_id == planilla.id).one()
planilla.total_ingresos, planilla.total_descuentos, planilla.total_aportes = (
    _d(row[0]), _d(row[1]), _d(row[2]))
planilla.total_neto = planilla.total_ingresos - planilla.total_descuentos
```

```python
sesiones = db.query(SesionUsuario).filter(
    SesionUsuario.usuario_id == usuario_id,
```

```python
sesiones = db.query(SesionUsuario).filter(
```

#### 1. `FormArticuloController.valores` itera todos los campos del esquema en cada cambio — `widgets/form_articulo_dinamico.dart` (getter `valores`, commit `05c81a03`)

**Problema:** `_onFormChanged` en `PantallaIngresoDirecto` consulta `_formCtrl.valores['marcaId']` para detectar si cambió la marca. Internamente `valores` llama a `_valores()`, que itera **todos** los campos del esquema en ese momento para construir un `Map` completo:

```dart
Map<String, dynamic> _valores() {
  final out = <String, dynamic>{};
  for (final f in widget.schema.campos) {   // ~15 campos en equipo_tecnologico
    out[f.key] = _rawValor(f);
  }
  return out;
}
```

Esto se ejecuta con cada cambio de cualquier campo del formulario (onChanged), recorriendo todos los campos del esquema y leyendo todos los controllers de texto, solo para extraer el valor de `marcaId`.

**Mejora sugerida:** exponer un método `getValor(String key)` en `FormArticuloController` que lea únicamente el controller del campo solicitado, evitando construir el mapa completo:

```dart
// En FormArticuloController:
dynamic getValor(String key) => _state?._rawValorByKey(key);

// En _FormArticuloDinamicoState:
dynamic _rawValorByKey(String key) {
  final f = widget.schema.campos.firstWhereOrNull((f) => f.key == key);
  if (f == null) return null;
  return _rawValor(f);
}
```

#### 2. `_cargarSchema` despacha tres `setState` separados — `screens/logistica/pantalla_ingreso_directo.dart` (líneas ~185-206, commit `05c81a03`)

**Problema:** `_cargarSchema` llama a `setState` tres veces para una sola operación lógica (inicio, resultado exitoso y limpieza del indicador), lo que provoca tres reconstrucciones del árbol de widgets cuando una sola sería suficiente:

```dart
setState(() { _cargandoSchema = true; _schemaError = null; });   // rebuild 1
// ...await...
setState(() { _schema = s; _formCtrl = ...; /* etc */ });         // rebuild 2
// finally:
if (mounted) setState(() => _cargandoSchema = false);             // rebuild 3
```

**Mejora sugerida:** incluir `_cargandoSchema = false` dentro del bloque de setState del resultado exitoso (y del catch), eliminando el tercer `setState`:

```dart
setState(() { _cargandoSchema = true; _schemaError = null; });
try {
  final s = await _svc!.formSchema(_clase);
  if (!mounted) return;
  setState(() {
    _schema = s;
    _formCtrl = FormArticuloController();
    // ...
    _cargandoSchema = false;   // ← merge aquí
  });
} catch (e) {
  if (!mounted) return;
  setState(() {
    _schemaError = ...;
    _cargandoSchema = false;   // ← merge aquí
  });
}
```

#### 3. `_marcarBase` recarga todos los conceptos desde el servidor — `screens/finanzas/pantalla_planilla.dart` (líneas ~106-109, commit `05c81a03`)

**Problema:** tras marcar un concepto como base, se llama a `_cargarConceptos()` que hace una petición completa al servidor para actualizar la lista, cuando solo cambió el campo `esBase` de un elemento ya conocido:

```dart
if (r.ok) {
  mostrarOk(context, '"${c.nombre}" marcado como concepto base (sueldo).');
  _cargarConceptos();   // round-trip innecesario
}
```

**Mejora sugerida:** actualizar el estado local directamente y llamar a `setState` sin round-trip:

```dart
if (r.ok) {
  mostrarOk(context, '"${c.nombre}" marcado como concepto base (sueldo).');
  setState(() {
    for (final concepto in _conceptos) {
      concepto.esBase = concepto.id == c.id;
    }
  });
}
```

Esto asume que `ConceptoRemunerativo.esBase` es mutable; si es immutable, se puede reconstruir la lista con `copyWith`.

```dart
FinanzasService? _finanzasSvc;

@override

  super.initState();
  getFinanzasService().then((s) => _finanzasSvc = s);
  _cargarTasaIgv();
}

Future<void> _cargarTasaIgv() async {
  final svc = _finanzasSvc ?? await getFinanzasService();
  ...
}
```
