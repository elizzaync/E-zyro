### Hallazgos

#### 1. Problema N+1 en `listar_programacion` — `BACKEND/app/routers/programacion_campo.py` (líneas ~43–57 y ~142–148)

La función `_to_out(pc, db)` ejecuta **dos consultas SQL por cada `ProgramacionCampo`** devuelta: una JOIN triple `ProgramacionEmpleado + Empleado + Usuario`, y una consulta separada para `Proyecto.nombre_proyecto`. Al llamar `return [_to_out(pc, db) for pc in filas]` con N programaciones en respuesta, esto genera `1 + 2N` queries.

**Mejora sugerida:** traer proyecto y empleados de todos los `ProgramacionCampo` devueltos en consultas únicas fuera de `_to_out`, construyendo diccionarios indexados por ID antes del loop.

---

#### 2. Carga completa de historial en Python para filtrar un único paso — `BACKEND/app/routers/equipos_intervenidos.py` (~líneas 495–526)

El endpoint `antecedente_procedimiento` carga **todas las filas de `HistorialInspeccion`** del equipo y luego itera en Python sobre cada `resultado` (JSON array) buscando el paso con `"orden" == orden`:

```python
for hi in rows:
    for p in (hi.resultado or []):
        if p.get("orden") != orden:
            continue
```

Para un equipo con muchas sesiones de inspección, trae a memoria todos los resultados JSON aunque la mayoría no coincidan con el `orden` solicitado.

**Mejora sugerida:** usar un operador JSONB de PostgreSQL en la cláusula `.filter()` para descartar en la DB las filas sin el paso buscado (p. ej. `HistorialInspeccion.resultado.contains([{"orden": orden}])` o con `cast`/`func.jsonb_path_exists`).

---

#### 3. Consulta de circuitos sin filtro `empresa_id` — `BACKEND/app/routers/equipos_intervenidos.py` (líneas ~253–259)

En `generar_pdf_directorio`, la consulta de circuitos omite el filtro `empresa_id`:

```python
circuitos = (
    db.query(TableroCircuito)
    .filter(TableroCircuito.equipo_intervenido_id == equipo_id)  # ← sin empresa_id
    .order_by(TableroCircuito.orden.asc())
    .all()
)
```

El equipo es validado contra `empresa_id` antes de llegar a esta query, por lo que no hay fuga de datos real (la FK CASCADE garantiza que los circuitos pertenecen al mismo tenant). Aun así es inconsistente con el resto del CRUD donde ambas columnas siempre se usan juntas como clave compuesta de tenant.

**Mejora sugerida:** agregar `.filter(TableroCircuito.empresa_id == empresa_id)` para coherencia y defensa en profundidad.

---

#### 4. `Empleado` se selecciona en la query de `_to_out` pero no se usa — `BACKEND/app/routers/programacion_campo.py` (líneas ~43–57)

La tupla devuelta es `(ProgramacionEmpleado, Empleado, Usuario)`, pero en el list-comprehension solo se usan `pe` y `u`; `e` (Empleado) se destrucctura y se ignora. SQLAlchemy aún carga todas las columnas del modelo `Empleado`.

**Mejora sugerida:** cambiar el `db.query(...)` a `db.query(ProgramacionEmpleado, Usuario)` conservando los JOINs necesarios para llegar a `Usuario` vía `Empleado`.

### Hallazgos

#### 1. Imágenes de hallazgos codificadas en base64 sin límite de tamaño — `e_zyro_app/lib/screens/pantalla_informe_termografico.dart` (líneas ~536–543)

Cada imagen del informe termográfico se carga completa en memoria y se convierte a base64 antes de enviarla:

```dart
final bytes = await file.readAsBytes();
return 'data:$mime;base64,${base64Encode(bytes)}';
```

Con varios hallazgos (cada uno admite 2 fotos), el payload JSON enviado al backend puede superar los varios MB. Una foto de 4 MB se transforma en ~5,3 MB de base64; con 5 hallazgos y 2 fotos cada uno eso son ~53 MB en memoria y en la petición HTTP.

**Mejora sugerida:** subir las imágenes a Cloudinary de forma independiente antes de generar el PDF (como ya se hace en `PantallaCamaraCampo`) y enviar solo las URLs. Alternativamente, escalar/comprimir la imagen antes de codificarla usando `image_picker`'s `maxWidth`/`maxHeight`/`imageQuality`.

#### 2. `TextEditingController`s sin `dispose` en `_editarNotas` — `e_zyro_app/lib/screens/pantalla_intervencion_equipo.dart` (líneas ~179–231)

Los dos controladores `obsCtrl` y `recCtrl` se crean dentro del método `_editarNotas` pero nunca se llama `.dispose()` sobre ellos:

```dart
final obsCtrl = TextEditingController(text: paso.observacion ?? '');
final recCtrl  = TextEditingController(text: paso.recomendacion ?? '');
```

Flutter recomienda llamar `dispose()` en todos los `TextEditingController` para liberar recursos del texto. Aunque en la práctica el GC los recupera al salir del método, omitirlo genera warnings en modo debug y puede causar leaks sutiles si el widget subyacente tarda en destruirse.

**Mejora sugerida:** agregar al final del método (tras el `await showModalBottomSheet`):
```dart
obsCtrl.dispose();
recCtrl.dispose();
```

#### 3. `getMiProgramacion` descarga todas las asignaciones futuras para filtrar hoy en cliente — `e_zyro_app/lib/screens/pantalla_principal.dart` (líneas ~113–124) y `e_zyro_app/lib/services/programacion_campo_service.dart`

El endpoint `/programacion-campo/mia` devuelve todas las asignaciones del empleado desde hoy en adelante. El cliente filtra:

```dart
_cuadrillaHoy = todas.where((p) => p.fecha == _hoyIso).toList();
```

Para un empleado con muchas asignaciones futuras programadas, esto transfiere datos innecesarios en cada carga de pantalla principal.

**Mejora sugerida:** agregar un parámetro `?fecha=` al endpoint backend (`/programacion-campo/mia`) para que pueda devolver solo las asignaciones de una fecha específica, y pasarlo desde el cliente.
