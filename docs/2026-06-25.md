**1. `BACKEND/app/routers/logistica.py` — Almacén no determinístico cuando hay stock en múltiples almacenes**

_Commit `0e4945c8`, bloque `alm_map` (aprox. líneas 800–820 en el archivo resultante)._

La consulta que construye `alm_map` no incluye `ORDER BY`, por lo que cuando un material tiene stock en más de un almacén el registro "ganador" depende del plan de ejecución del motor y puede variar entre peticiones:

```python
for row_a in (
    db.query(Stock.material_id, Stock.almacen_id, Almacen.nombre)
    .outerjoin(Almacen, Almacen.id == Stock.almacen_id)
    .filter(Stock.material_id.in_(mat_ids), Stock.empresa_id == empresa_id)
    .all()          # ← sin ORDER BY
):
    mid = str(row_a.material_id)
    if mid not in seen_alm:
        seen_alm.add(mid)
        alm_map[mid] = (...)
```

**Sugerencia:** añadir `.order_by(Stock.updated_at.desc())` (o el criterio que ya usaba el helper `_material_out` original) para que el almacén devuelto sea estable.

**2. `BACKEND/app/routers/privilegios.py` — `permisos_usuario` no filtra la tabla `permiso` por empresa**

_Commit `ecf59bc3`, endpoint `GET /usuarios/{id}/permisos` (~línea 118)._

La query retorna todos los registros de la tabla `permiso` sin filtrar por `empresa_id`. Si el catálogo de permisos es global (compartido entre empresas) esto es correcto; pero si la tabla llega a ser multi-tenant la consulta expondría módulos de otras empresas. Conviene documentar explícitamente el alcance de la tabla `permiso` para evitar confusión futura.

**3. `BACKEND/app/routers/logistica.py` — N+1 query residual en `_material_out` para `marca_id`**

### Hallazgos

**1. `e_zyro_app/lib/screens/pantalla_evaluaciones.dart` — Doble recorrido innecesario de `_empleados`**

_Aprox. líneas 219–222 del archivo resultante._

```dart
_sel = _empleados.where((e) => e.id == pre.id).firstOrNull ?? pre;
if (_empleados.where((e) => e.id == pre.id).isEmpty) _empleados = [pre, ..._empleados];
```

La lista `_empleados` se itera dos veces con el mismo predicado. Si la lista es larga (empresas con muchos empleados) el costo se duplica sin necesidad.

**Sugerencia:**
```dart
final found = _empleados.where((e) => e.id == pre.id).firstOrNull;
_sel = found ?? pre;
if (found == null) _empleados = [pre, ..._empleados];
```

**2. `e_zyro_app/lib/screens/pantalla_privilegios.dart` — Bug: doble incremento de `permisosDirectos`**

_Método `_togglePermiso`, aprox. líneas 196–212._

```dart
setState(() {
    p.directo = true;
    _seleccionado!.permisosDirectos++;           // incrementa el objeto
    final idx = _usuarios.indexWhere((u) => u.id == uid);
    if (idx >= 0) _usuarios[idx].permisosDirectos++;  // mismo objeto → doble incremento
});
```

`_seleccionado` es la misma referencia de objeto que el elemento correspondiente en `_usuarios` (ambas listas apuntan a las mismas instancias de `_Usuario`). Los dos incrementos actúan sobre el mismo campo, produciendo un conteo incorrecto de privilegios en el panel lateral. El badge "N privilegios extra" mostrará el doble del valor real.

**Sugerencia:** eliminar el bloque `indexWhere`; el incremento sobre `_seleccionado!` ya actualiza el objeto en `_usuarios`:
```dart
setState(() {
    p.directo = true;
    _seleccionado!.permisosDirectos++;
});
```
Lo mismo aplica al bloque de decremento en la rama `else`.

**3. `e_zyro_app/lib/screens/pantalla_privilegios.dart` — Doble `.where()` en `_ModuloCard.build()`**

_Aprox. líneas 762–763._

```dart
final directos = permisos.where((p) => p.directo).length;
final viaRol   = permisos.where((p) => p.viaRol && !p.directo).length;
```

Cada rebuild de la tarjeta de módulo recorre `permisos` dos veces. Dado que `build()` puede llamarse con frecuencia (scrolling, cambios de estado), esto suma iteraciones innecesarias.

**Sugerencia:** usar un único `fold`:
```dart
var directos = 0, viaRol = 0;
for (final p in permisos) {
    if (p.directo) directos++;
    else if (p.viaRol) viaRol++;
}
```

**4. `e_zyro_app/lib/screens/pantalla_camara_campo.dart` — `SharedPreferences.getInstance()` llamado dos veces en el flujo de inicialización**

_Métodos `_restaurarSeleccion` (línea ~102) y `_guardarSeleccion` (línea ~124), llamados en secuencia desde `_inicializar`._

Cada uno llama `SharedPreferences.getInstance()` por separado. Aunque la implementación subyacente cachea la instancia, el patrón lleva a duplicación innecesaria. Sería más claro obtener `prefs` una sola vez en `_inicializar` y pasarlo a los métodos que lo necesitan.
