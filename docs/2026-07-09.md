**`0fd9c07e` — fix(audit): excluir 403 del candado ClienteExterno en cualquier ruta**
*(autor: E-System TIC, 13:42 -0500)*

Archivos modificados: `BACKEND/app/core/audit_events.py` (+9 / -8).

El middleware de auditoría solo suprimía el ruido de 403 para rutas bajo
`/portal-cliente`, pero el candado de rol en `security.py` devuelve 403 por
diseño en *cualquier* ruta fuera de `/portal-cliente` y `/auth` cuando el rol
es `ClienteExterno`. Esto generaba ráfagas de eventos `PERMISSION_DENIED`
reales que activaban falsas alertas (caso documentado: 12 denegaciones para
Portal TALMA S.A. en 15 min). El fix reemplaza la comparación de prefijo de
ruta por una verificación del claim `rol` del JWT; si el rol es
`clienteexterno` y la ruta *no* es de portal/auth, el evento se omite. La
constante `_PREFIJOS_PORTAL` ahora se importa desde `security.py` en lugar de
duplicarse.

### Hallazgos

#### 1. `descripcion` sin truncar antes de crear el ticket (riesgo de correctitud)
**Archivo:** `BACKEND/app/routers/auth.py` — función `soporte_acceso` (≈ línea 800)

`nombre` y `email` se truncan a 120 y 150 caracteres respectivamente antes de
procesarse, pero `descripcion` solo se trunca en el evento de `audit_log`
(`[:500]`), no antes de pasarse al cuerpo del ticket. Un actor anónimo
(endpoint público sin autenticación) puede enviar una descripción
arbitrariamente larga que se escribirá tal cual en la base de datos a través
de `crear_ticket`. Sugerencia: aplicar el mismo truncado explícito —
`descripcion = descripcion[:2000]` o similar — antes de construir el ticket.

---

#### 2. `print()` para capturar errores en producción (mala práctica)
**Archivo:** `BACKEND/app/routers/auth.py` — función `soporte_acceso` (≈ línea 843)

```python
except Exception as exc:
    print(f"[soporte-acceso] error creando ticket: {exc}")
```

El `except` silencia el fallo y solo emite un `print` a stdout. Si el proceso
corre tras un proxy WSGI que no redirige stdout a un sistema de logs (Gunicorn
con worker silencioso, Railway, etc.), el error desaparece sin dejar rastro en
`audit_log` ni en el sistema de monitoreo. Sugerencia: usar el logger del
proyecto (`logger.exception(...)`) y/o registrar el evento con
`registrar_evento(accion="ERROR", ...)` igual que se hace en otros endpoints.

---

#### 3. Importaciones dentro del cuerpo de función (fragilidad ante importaciones circulares)
**Archivos:**
- `BACKEND/app/routers/auth.py` — `soporte_acceso` (≈ línea 824): `from app.routers.soporte import CrearTicketBody, crear_ticket`
- `BACKEND/app/routers/portal_cliente.py` — `portal_crear_ticket` (≈ línea 1476): misma importación

Las importaciones diferidas dentro de funciones son un patrón que indica (y
enmascara) dependencias circulares entre módulos. Python cachea los módulos tras
la primera carga, por lo que no hay impacto de rendimiento medible, pero el
patrón dificulta detectar qué módulo introduce el ciclo. Sugerencia: resolver
la dependencia circular elevando la lógica compartida a un módulo de servicios
(`app/services/soporte.py`) e importar desde allí a nivel de módulo.

#### 4. Consulta sin paginación en `portal_tickets` (riesgo de rendimiento)
**Archivo:** `BACKEND/app/routers/portal_cliente.py` — función `portal_tickets` (≈ línea 1436)

```python
rows = (
    db.query(TicketSoporte)
    .filter(...)
    .order_by(TicketSoporte.created_at.desc())
    .all()
)
```

El `.all()` carga todos los tickets del usuario en memoria de una sola vez. Una
empresa con un historial largo de tickets devolverá una lista creciente sin
límite. Sugerencia: añadir un parámetro `limit` (por defecto 50 o 100) y un
cursor o parámetro `offset` para paginación, igual que otros endpoints de lista
del portal.

#### 5. Índices posicionales en el mapeo de filas SQL (fragilidad ante cambios en la query)
**Archivo:** `BACKEND/app/routers/portal_cliente.py` — función `portal_equipos_historial` (≈ líneas 795–796)

```python
"sede":   r[14],
"region": r[15],
```

El mapeo usa índices posicionales sobre el resultado de la query SQL nativa. Si
en el futuro se agrega o reordena alguna columna en el `SELECT`, estos índices
devuelven datos incorrectos en silencio sin producir un error. Es un patrón
preexistente en el archivo (extendido por este commit), pero el riesgo crece
con cada columna nueva. Sugerencia: usar `text(...).columns(...)` de SQLAlchemy
o un `namedtuple`/`Row._mapping` para acceder a columnas por nombre.
